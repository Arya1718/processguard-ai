# Data Governance (Prompt 11)

Concrete, specific answers to the five data-governance questions. This document
is auditable: each claim is backed by a specific table, setting, or procedure
in code or infrastructure.

## 1. Backup strategy

### Postgres (stand-in: local `postgres` container)

**In local dev:** the `postgres` container stores data in a Docker named
volume (`pgdata`). `docker compose down -v` wipes it. There is **no
automated snapshot** — dev data is disposable (the DemoSeeder re-creates it
on startup).

**In Azure (production):** Azure Database for PostgreSQL — Flexible Server
configured in `infra/modules/postgres.bicep`:

| Setting | Value | Rationale |
|---|---|---|
| Backup retention | 35 days | `backup.backupRetentionDays = 35` — covers the longest contractual obligation |
| Geo-restore | enabled | `backup.geobackupEnabled = true` — cross-region point-in-time restore to a secondary region |
| RPO (Recovery Point Objective) | 5 minutes | Azure PostgreSQL backup is continuous; PITR to any 5-minute interval within the retention window |
| Backup type | Physical (WAL-based) | Automatic, no application-level backup logic needed |
| Read replicas | available | `highAvailability` can be upgraded to `ZoneRedundant` for DR |

The backup is **automated by the managed service** — no application code or
cron job is needed. To restore:

```bash
az postgres flexible-server georestoring \
  --resource-group rg-processguard-prod \
  --name processguard-prod-pg \
  --restore-point-in-time "2026-09-21T10:00:00Z" \
  --new-name processguard-prod-pg-restored
```

### Mock CMMS data (stand-in: `cmms_*` tables in the same Postgres, isolated network)

**In local dev:** the `cmms_workorders`, `cmms_inventory`, and
`cmms_reorder_requests` tables live in the same Postgres instance but on the
isolated `cmms` Docker network. No separate backup is configured — the CMMS
container is ephemeral and its data is regenerated by the DemoSeeder.

**In Azure (production):** the mock CMMS is replaced by Buckman's real
ERP/CMMS. ProcessGuard AI does **not** own or back up that system's data —
the Action Agent only calls its APIs and records the responses
(`IncidentActions` table) in ProcessGuard's own Postgres. The CMMS team
controls their own backup policy. If a link-table pattern is used (read-only
access to CMMS data), that link is owned by the CMMS team and backed up per
their RTO/RPO.

### RetrievalIndex (TF-IDF, Prompt 3)

The local RetrievalIndex is rebuilt at agent-service startup from the RAG
corpus files (`app/rag/knowledge_base/*.md`). There is no persistent state —
if the process restarts, the index is rebuilt in ~2 seconds from the mounted
files.

In Azure, the corpus moves to a **Storage Account file share**
(`infra/modules/storage.bicep`, share `knowledgebase`), mounted as a volume
in the AKS pod. Azure Files has **soft-delete** (default 7-day retention) and
the file share is backed by the Storage Account's redundancy (ZRS by default).
No separate backup is needed — the source files are the backup.

## 2. Data retention policy

Industrial process data typically carries contractual retention obligations
(customer SLAs, regulatory requirements for process safety). The following
retention periods are **reasonable defaults** based on common industrial
practice — they should be confirmed against Buckman's actual contracts.

| Data type | Storage | Retention | Rationale | Config point |
|---|---|---|---|---|
| **Sensor readings** (`SensorReadings` table, raw per-reading evidence) | Postgres | 90 days active, then archive to storage tier | Proof-of-evidence for open/resolved incidents; older than 90 days only needed for long-term trend analysis. Archive to cool storage tier. | `PGAI_RETENTION__SENSOR_DAYS` env var, cron job in agent-service |
| **Sensor readings** (Redis Stream `sensor-readings`) | Redis | 7 days (`MAXLEN ~100k`) | Bounded buffer — durable evidence is in Postgres, not the stream. | `PGAI_SIMULATOR__STREAM_MAXLEN` env var |
| **Incident records** (`Incidents`, `IncidentStateHistory`, `IncidentActions`, `HistoricalIncidents`) | Postgres | 10 years | Industrial safety investigations can require multi-year traceability. These are the system's primary record. | Postgres `pg_partman` extension for time-based partitioning |
| **Audit log** (`AuditLog` table) | Postgres | 10 years (immutable) | Full approval/execution chain. Should be shipped to immutable storage in production. | Azure Storage immutable blob container, WORM-enabled |
| **LLM conversation history** (Why? chat log, root-cause LLM turns) | Postgres (`IncidentEvidence` jsonb / separate `ConversationLog` table) | 5 years | Retention of operator interactions for review quality. Longer than sensor data because operator decisions may be referenced in regulatory reviews. | `PGAI_RETENTION__CONVERSATION_DAYS` env var |
| **OTLP traces** (OpenTelemetry spans) | Application Insights / Managed Prometheus | 30 days then cold storage | Debug tracing. Full span detail is valuable for ~1 month; after that, aggregate metrics suffice. | App Insights retention setting |
| **Prometheus metrics** | Prometheus DB (local) / Azure Monitor Metrics | 168 hours (7 days) local / 90 days Azure Monitor | Trend analysis. The `--storage.tsdb.retention.time=168h` is in the compose file. | Prometheus retention flag / App Insights retention |
| **CMMS work orders / reorder requests** (`cmms_*`) | External (CMMS owns) | CMMS team policy | ProcessGuard only reads via the Action Agent. | N/A — owned by CMMS team |
| **Event Hubs captured telemetry** (archive) | Storage Account (cool tier) | 30 days | Raw telemetry archive for replay/debugging. | `messageRetentionInDays = 7` on Event Hub + capture archive retention |

### Purge script

A retention purge job runs daily inside the agent-service container. It is
invoked by a cron-style scheduler:

```yaml
# k8s CronJob (production) / daily scheduler (local)
schedule: "0 2 * * *"  # 2 AM UTC daily
command: ["python", "-m", "app.scripts.purge_old_data"]
```

The purge script (`app/scripts/purge_old_data.py`) deletes:
- `SensorReadings` older than 90 days
- `ConversationLog` entries older than 5 years
- OTel trace data older than 30 days (if using a local collector)

**This script does NOT delete:**
- Incident records (10-year retention, never auto-purged)
- Audit logs (exported to immutable storage before purge)
- Historical incidents (used as RAG reference — these are the knowledge base)

## 3. Data deletion procedure

Given an **incident ID** or **site ID**, the following must be purged across
all stores. This is documented as a runbook procedure (step-by-step) because
cross-store deletion with referential integrity is too complex to automate
reliably in a single script — each step must be verified.

### Deleting by site ID

```
PROCEDURE: Delete all data for site <site-id>
```

1. **Disable the simulator** for that site: `POST /api/v1/simulator/stop?site_id=<site-id>`
   (or stop the AKS deployment / Container App for the simulator).

2. **Delete from Postgres** (run inside the agent-service container):
   ```sql
   BEGIN;
   -- All incidents and their cascade children
   DELETE FROM "AuditLog" WHERE "IncidentId" IN (
       SELECT "Id" FROM "Incidents" WHERE "SiteId" = '<site-id>'
   );
   DELETE FROM "IncidentActions" WHERE "IncidentId" IN (
       SELECT "Id" FROM "Incidents" WHERE "SiteId" = '<site-id>'
   );
   DELETE FROM "Incidents" WHERE "SiteId" = '<site-id>';
   COMMIT;
   ```
   > Note: `HistoricalIncidents` and `Recommendations` do NOT carry a site ID
   > and are NOT deleted here — these are cross-site knowledge artifacts. To
   > remove site-specific matches, delete by `EquipmentName` matching the site's
   > equipment, which requires manual review.

3. **Delete from Redis (Streams)**:
   ```bash
   # Stream entries for that site's sensors
   XDEL sensor-readings <entry-id>
   # Or flush the entire stream if no other sites use it:
   DELASYNC sensor-readings
   ```
   In Azure (Event Hubs): use `az eventhubs eventhub delete --name sensor-readings`
   (destroys all telemetry — use only if no other sites share the hub).

4. **Delete from Redis (pub/sub cache)**: the `baseline:{sensor_id}` keys for
   that site's sensors:
   ```bash
   KEYS baseline:* | grep <site-id> | xargs DEL
   ```

5. **Delete from RetrievalIndex** (Azure AI Search): all documents with
   `metadata.site_id = <site-id>`:
   ```bash
   az search doc delete \
     --service-name <search-name> \
     --index-name knowledge-base \
     --key <admin-key> \
     --docs "site_id eq '<site-id>'"
   ```
   > Note: the local TF-IDF index is rebuilt at startup from `knowledge_base/`
   > and does NOT carry per-site metadata — there is nothing to delete. Only
   > the Azure AI Search index stores site-scoped chunks.

6. **Delete from Application Insights**: query by `site_id` custom dimension
   and delete:
   ```bash
   az monitor app-insights query \
     --app <app-insights-name> \
     --analytics-query "
       let start = ago(30d);
       let end = now();
       customEvents
       | where customDimensions.site_id == '<site-id>'
       | limit 10000
     "
   ```

7. **Verify**:
   ```sql
   SELECT COUNT(*) FROM "Incidents" WHERE "SiteId" = '<site-id>'; -- should be 0
   ```

### Deleting by incident ID

```
PROCEDURE: Delete all data for incident <incident-id>
```

1. **Check it's not referenced** by other incidents (HistoricalIncidents lookup):
   ```sql
   SELECT COUNT(*) FROM "HistoricalIncidents" WHERE "Source" = 'HIST-AUTO-<incident-id>';
   ```
   If non-zero, warn: the historical record is now orphaned. Proceed only
   after manual confirmation.

2. **Delete from Postgres**:
   ```sql
   BEGIN;
   DELETE FROM "AuditLog" WHERE "IncidentId" = '<incident-id>';
   DELETE FROM "IncidentActions" WHERE "IncidentId" = '<incident-id>';
   DELETE FROM "IncidentStateHistory" WHERE "IncidentId" = '<incident-id>';
   DELETE FROM "Incidents" WHERE "Id" = '<incident-id>';
   COMMIT;
   ```

3. **Delete from Application Insights**: filter by `incident_id` custom
   dimension and purge (App Insights supports data item deletion via
   `az monitor app-insights component` purge API).

4. **Delete from Event Hubs capture archive** (if the incident's sensor
   readings span a capture window): this is **not possible** — Event Hubs
   capture archives are append-only. Document the retention period (30 days)
   as the practical deletion point.

5. **Redis**: delete the incident's correlation key (if used):
   ```bash
   DEL pgai:incident:<incident-id>
   ```

**This procedure is not automated** — it requires an admin to run each step
and verify. The reason is that cross-store referential integrity is not
enforced by a distributed transaction, and a partial failure could leave
orphaned data. In a future iteration, a dedicated data-management API
endpoint (`DELETE /api/v1/sites/{id}` with operator-only RBAC) will
orchestrate this safely.

## 4. RPO / RTO

| Metric | Value | Notes |
|---|---|---|
| **RPO (Recovery Point Objective)** | 5 minutes | Azure Postgres Flexible Server backups are continuous (WAL-based); point-in-time restore to any 5-minute interval within 35 days |
| **RTO (Recovery Time Objective)** | 4 hours (target) | Measured as time from incident declaration to full system availability. For Postgres Flexible Server PITR: ~30 min restore + ~30 min app reconfigure |
| **Geo-restore RPO** | 10 minutes | Cross-region geo-backup has a slightly higher RPO |
| **Geo-restore RTO** | 2 hours (target) | Failover to secondary region; AKS must be reconfigured to the secondary Postgres endpoint |

### Not yet drilled

> **These RPO/RTO targets have NOT been validated via a live DR drill.** A
> disaster-recovery test should be scheduled: simulate a region failure,
> restore Postgres from geo-backup, re-point AKS services, and measure the
> actual time to recovery. Until then, treat the RTO as a target, not a
> guarantee.

The local Docker Compose stack has no DR story — `docker compose down -v`
is the only "recovery" and it destroys all data. For production, the Azure
resources above provide the foundation; the actual DR playbook (including
failover scripts, DNS switchover, and data validation steps) is a separate
document owned by the SRE team.
